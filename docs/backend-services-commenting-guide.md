# Backend Services 注释增强风格指南（LLM 可执行）

## 1. 适用范围与目标

- 适用范围：`backend/app/services` 下的 Python 服务层代码。
- 目标：在**不改变业务逻辑**的前提下，提高可读性、可维护性、排障效率。
- 读者对象：人类开发者 + 大模型代码助手（可按本指南直接补注释）。

---

## 2. 注释分层规范（模块 / 类 / 函数 / 行内）

### 2.1 模块级注释（必须）

放在文件最顶部三引号 docstring，回答：

- 这个模块负责什么。
- 它不负责什么（边界）。
- 关键约束（例如 key 规则、状态机约束、幂等策略）。

建议 4-12 行，避免“流水账式背景介绍”。

### 2.2 类级注释（按需）

当类具有状态机、生命周期、并发语义时必须写；纯数据容器可写一行。

### 2.3 函数级 docstring（关键函数必须）

对编排函数、跨服务调用函数、带回滚补偿函数、状态流转函数必须写。

必须说明：

- 输入/输出语义（不是类型重复）。
- 副作用（DB 提交、外部调用、对象写入/删除）。
- 失败语义（什么情况下返回错误/抛异常）。

### 2.4 行内注释（稀疏但关键）

只用于复杂分支前，解释“为什么这么做”。

推荐场景：

- 并发冲突处理。
- 补偿清理逻辑。
- 状态机切换点。
- 兼容性兜底分支。

---

## 3. MUST / MUST NOT 规则

### MUST

- 使用中文注释，术语统一（见术语表）。
- 关键编排函数必须有 docstring。
- 发生副作用（写 DB/写对象存储/调用下游）要在 docstring 中说明。
- 注释与代码冲突时，以代码为准并立即修注释。
- 注释任务只做注释增强，不改逻辑、不重构。

### MUST NOT

- 不写“代码翻译型”注释（例如 `# 把 x 赋值给 y`）。
- 不重复类型注解已表达的信息。
- 不写过时设计文档式长注释（与当前实现不一致）。
- 不在注释任务里顺手修改业务行为。
- 不增加无法从代码验证的承诺性描述。

## 4. 标准模板（可直接复制）

### 4.1 模块模板

```python
"""<模块名>。

职责：
1. ...
2. ...

说明：
- ...（边界）
- ...（关键约束）
"""
```

### 4.2 关键函数模板

```python
def func(...):
    """一句话摘要。

    约束：
    - ...
    - ...

    副作用：
    - ...
    """
```

### 4.3 复杂分支行内注释模板

```python
# 并发场景下可能命中唯一约束：回滚后复用已有记录，避免重复对象。
```

## 5. 典型示例（backend/services）

### 5.1 `minio_storage` 场景

- 模块注释说明单桶策略与 key 前缀规则。
- `upload_image_bytes` docstring 要明确“sha256 去重 + 已存在复用”。
- `object_exists` 需说明“仅缺失类错误返回 False，其他错误继续抛出”。

### 5.2 `document_upload_service` 场景

- `resolve_file_record` 说明三分支：新建/复用/缺失修复。
- `persist_document` 标注并发冲突后的补偿清理目的。
- 对修复路径写明为何要更新 `FileRecord` 指向。

### 5.3 `document_parsing_task_service` 场景

- `create_or_reuse_*` 说明“同文档进行中任务复用”的约束。
- `claim_next_pending_*` 说明 `FOR UPDATE SKIP LOCKED` 的并发意图。
- `recover_orphaned_*` 说明进程重启后为何把 running 标记为 failed。

## 6. 反例与改写示例（坏注释 -> 好注释）

### 反例 1：重复代码表面含义

```python
# 设置状态为 running
task.status = DocumentParsingTaskStatus.running
```

改写：

```python
# 任务领取后立即切到 running，避免被其他 worker 重复消费。
task.status = DocumentParsingTaskStatus.running
```

### 反例 2：信息不完整

```python
"""保存图片信息。"""
```

改写：

```python
"""批量落库图片元数据。

约束：按 file_hash 去重，冲突时 DO NOTHING，不中断主流程。
"""
```

### 反例 3：与实现脱节

```python
# 这里会自动重试 3 次
```

改写：

```python
# 当前分支不做自动重试，失败后由任务状态返回 failed。
```

## 7. 自检清单（提交前 10 条）

1. 是否仅修改注释/文档，未改变业务逻辑？
2. 模块顶部是否有职责与边界说明？
3. 关键编排函数是否有 docstring？
4. docstring 是否写出副作用与失败语义？
5. 是否避免了“翻译代码”的低价值注释？
6. 复杂分支是否有“为什么”的注释？
7. 术语是否统一（文档解析任务/去重复用/失败兜底）？
8. 注释是否与当前实现一致、无过时描述？
9. 是否避免承诺未实现行为（重试、幂等范围等）？
10. 是否通过基础语法检查（如 `python -m compileall`）？

## 8. 给大模型的执行指令模板（可直接使用）

```text
任务：仅对 backend/app/services 下代码做中文注释增强，不改业务逻辑。

执行约束：
1) 只改注释/docstring；禁止修改函数签名、控制流、数据库语义、接口协议。
2) 注释遵循四层：模块、类、关键函数、复杂分支行内注释。
3) 注释重点写“为什么/约束/失败语义”，不要翻译代码字面含义。
4) 对以下场景必须补注释：并发冲突处理、补偿清理、状态流转、外部调用失败语义。
5) 若注释与代码冲突，以代码为准并修正注释。

输出要求：
- 列出修改文件。
- 简述每个文件补充了哪些注释层级。
- 说明已确认“无业务逻辑改动”。
```

## 术语表（统一用词）

- 文档解析任务：Document Parsing Task
- 去重复用：Dedup Reuse
- 缺失对象修复：Missing Object Repair
- 失败兜底：Fail-safe
- 补偿清理：Compensation Cleanup
