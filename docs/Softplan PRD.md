# 软件项目成本估算分析平台 PRD

## 1. 文档信息

**文档名称**：软件项目成本估算分析平台 PRD  
**产品阶段**：项目启动阶段 / MVP 定义  
**产品形态**：Web 应用  
**项目属性**：开源工具、研究与工程结合的分析平台  
**当前版本**：V0.1

---

## 2. 项目概述

### 2.1 项目一句话定义

Softplan（Software Effort and Cost Planning System），一个基于大模型的软件项目规模与成本估算分析平台，能够从项目文档中自动提取需求信息，进行功能点分析与成本估算，并允许用户在分析过程中进行审阅、修正和重新估算。

### 2.2 项目定位

本项目不是传统意义上的企业级商业系统，而是一个偏研究与工程实践的开源分析平台。  
它强调：

- 自动化优先
- 高可解释性
- 支持人工介入
- 方法可扩展
- 面向项目分析而非简单结果展示

### 2.3 产品类型

本产品的核心定位是：

**分析平台（Analysis Platform）**

而不是：

- 单纯的估算计算器
- 面向商业交付的 SaaS 系统
- 仅输出结论的黑盒工具

平台更关注“分析过程 + 中间结果 + 最终估算”的完整链路。

---

## 3. 背景与目标

### 3.1 背景

在软件项目成本估算场景中，传统方法通常存在以下问题：

- 需求文档内容复杂，人工分析成本高
- 功能点识别依赖经验，主观性较强
- 估算过程不透明，复核困难
- 成本模型与功能点方法往往相互耦合，扩展性差
- 缺少一个可持续实验、对比和迭代的方法平台

随着大模型在文档理解、结构抽取与文本推理方面的能力提升，构建一个能够辅助甚至自动完成需求分析与估算的系统具备现实意义。

### 3.2 核心目标

本项目希望解决的问题是：

**让软件项目的规模与成本估算，从“依赖人工经验的离散过程”，转变为“可自动化、可审阅、可修正、可迭代的分析流程”。**

### 3.3 产品目标

1. 支持用户以项目为单位管理估算任务
2. 支持上传项目相关文档，并自动转化为结构化文本
3. 支持基于大模型的需求分析与功能识别
4. 优先支持 IFPUG 功能点分析
5. 支持中间结果展示与人工修改
6. 支持基于可扩展模型的工作量 / 成本估算
7. 支持保存历史估算、推理过程与修改记录
8. 支持形成结构化估算报告

### 3.4 非目标

当前阶段不追求：

- 商业化交付能力
- 完整企业权限体系
- 登录、注册、支付
- 高并发、多租户能力
- 复杂知识库、RAG 或模型微调体系
- 一开始就支持所有功能点方法和所有文档格式

## 4. 用户与使用场景

### 4.1 目标用户

本项目当前面向以下几类用户：

1. **软件工程研究者**  
   关注功能点分析、成本估算方法、AI 在软件工程中的应用。

2. **项目估算人员 / 项目经理**  
   希望通过系统提升需求分析与项目估算效率。

3. **软件开发团队成员**  
   希望在项目早期通过文档获得规模和成本的参考结果。

4. **开源使用者 / 实验用户**  
   希望快速运行一个可操作、可观察、可迭代的工具。

### 4.2 典型使用场景

#### 场景 1：新建项目并快速估算

用户创建项目，上传需求说明书或立项材料，系统自动解析文档，输出需求分析结果、功能点分析结果和初步成本估算。

#### 场景 2：人工修正中间分析结果

系统自动识别功能类型、数据实体或复杂度后，用户对其中不准确的部分进行修正，再触发重新计算。

#### 场景 3：多轮估算与版本对比

同一项目在需求变化后重新上传文档或修改分析结果，系统保存多个估算版本，便于比较差异。

#### 场景 4：研究不同方法的效果

平台后续支持多种功能点方法和成本模型时，研究者可以在相同项目上比较不同方法的结果差异。

## 5. 产品原则

### 5.1 自动化优先

系统默认应尽可能自动完成从文档到估算结果的主要流程，减少用户重复劳动。

### 5.2 高可解释性

系统不仅要给出结果，还应展示中间分析过程，包括识别出的功能、实体、分类依据、推理信息和计算过程。

### 5.3 用户可介入

用户不是被动接受结果，而是可以在关键节点进行确认、修改和重算。

### 5.4 方法可扩展

功能点分析方法、成本估算模型、文档解析方式应保持松耦合，便于未来扩展。

### 5.5 开源友好

架构、流程和模块设计应适合开源实现与迭代，而非一开始就依赖复杂企业基础设施。

### 5.6 简洁严谨

界面和交互应体现专业、干净、克制、可读的风格，避免花哨设计。

---

## 6. 产品范围

### 6.1 MVP 范围

MVP 目标是跑通一条完整链路：

**项目创建 → 文档上传 → 文档解析 → 需求分析 → IFPUG 功能点分析 → 成本估算 → 报告生成 → 人工修正与重算**

MVP 优先包含：

- 项目列表与项目创建
- 项目文档上传
- PDF 文档优先支持
- 文档转结构化文本
- 基于 LLM + Prompt 的分析流程
- IFPUG 方法优先支持
- 中间结果展示
- 人工修改中间结果
- 估算重跑
- 历史版本保存
- 报告查看

### 6.2 暂不纳入 MVP 的内容

- 登录与权限系统
- 支付与商业化能力
- 团队协作功能
- RAG / 微调 / 知识库
- 多种功能点方法的完整实现
- 所有文件格式的高质量支持
- 企业级部署运维能力
- 外部系统集成 API

## 7. 系统总体流程

### 7.1 主流程

1. 用户进入项目列表页
2. 新建项目并填写基础信息
3. 上传项目文档
4. 系统解析文档并转为结构化文本
5. 系统基于大模型进行需求分析
6. 系统识别功能、数据实体及相关中间信息
7. 系统执行功能点分析（优先 IFPUG）
8. 系统基于成本估算模型生成工作量 / 成本结果
9. 系统生成报告
10. 用户查看中间结果与最终结果
11. 用户可修改中间输出并重新估算
12. 系统保存版本、推理过程与修改记录

### 7.2 核心闭环

**文档输入 → 自动分析 → 中间结果可视化 → 人工修正 → 重新估算 → 结果沉淀**

## 9. 功能需求

## 9.1 项目管理模块

### 功能说明

用于管理估算任务的基本载体。

### 核心能力

- 查看项目列表
- 新建项目
- 编辑项目基础信息
- 删除项目（可后置）
- 进入项目分析工作台

### 项目基础信息建议字段

- 项目名称
- 项目描述
- 创建时间
- 更新时间
- 当前状态
- 当前估算版本

### 项目状态建议

- 未开始
- 已上传文档
- 解析中
- 分析中
- 待确认
- 已生成估算
- 已归档

---

## 9.2 文档输入与解析模块

### 功能说明

负责接收用户上传的项目资料，并将其转化为适合大模型处理的结构化文本输入。

### 核心能力

- 上传文档
- 查看文档列表
- 文档解析状态展示
- 文档预览（可后置）
- 文档转结构化文本
- 结构化文本查看

### 输入范围

原则上不限制文档来源与类型，但 MVP 阶段优先支持：

- PDF

未来可扩展：

- Word
- Markdown
- Excel
- 纯文本
- API 文档
- 其他半结构化材料

### 输出结果

- 文档元信息
- 转换后的结构化文本
- 文本分段 / 章节信息
- 可供后续分析调用的统一格式内容

### 设计要求

- 文档解析过程可追踪
- 转换结果可查看
- 允许用户发现并指出错误解析内容

---

## 9.3 需求分析模块

### 功能说明

基于结构化文本和大模型能力，对文档内容进行需求提取与项目分析。

### 核心能力

- 自动提取需求项
- 自动识别功能模块
- 自动识别业务对象 / 数据实体
- 输出分析摘要
- 展示分析依据
- 支持人工修正

### 输出内容示例

- 项目目标摘要
- 主要业务模块
- 功能清单
- 数据相关对象
- 不确定项 / 歧义项
- 待人工确认项

### 设计要求

- 输出尽可能结构化
- 对每一项分析结果保留来源依据
- 区分“系统明确识别”与“模型推测”

---

## 9.4 功能点分析模块

### 功能说明

在需求分析结果基础上，对功能进行功能点分类与计算。MVP 优先支持 IFPUG。

### 核心能力

- 自动生成功能点分析候选结果
- 支持识别功能类型
- 支持复杂度判断
- 支持中间计算展示
- 支持人工修改与重算

### MVP 支持策略

- 功能点方法采用可扩展设计
- 首期优先实现 IFPUG
- 后续预留多方法支持能力

### 中间结果建议展示

- 功能项名称
- 功能类型
- 涉及实体 / 文件
- 复杂度判断
- 计点依据
- 当前点数
- 模型解释
- 用户修正状态

### 设计要求

- 功能点结果不应是黑盒
- 用户应能直接改动中间结构
- 每次改动应触发版本化记录或重算机制

---

## 9.5 成本估算模块

### 功能说明

在功能点结果和其他可用特征基础上，输出工作量和成本估算结果。

### 核心能力

- 根据当前估算模型生成工作量估算
- 生成成本估算
- 展示估算输入特征
- 展示估算结果与解释信息
- 支持人工调整后重新估算

### 模型策略

当前阶段不固化单一成本模型。  
产品层面以“估算框架”视角设计，后续可接入：

- 基于规则的简单模型
- 基于统计学习的模型
- 基于 AutoML 的估算模型

### 估算输出建议

- 功能点规模结果
- 工作量结果
- 成本结果
- 影响因素说明
- 模型置信信息（如适用）
- 风险提示（如适用）

---

## 9.6 报告模块

### 功能说明

将项目估算过程中的关键内容组织为可阅读、可沉淀的分析报告。

### 报告建议结构

1. 项目概览
2. 输入文档说明
3. 需求分析摘要
4. 功能识别结果
5. 功能点分析结果
6. 成本估算结果
7. 关键假设与限制
8. 修改记录与版本说明

### 核心能力

- 在线查看报告
- 报告结构化呈现
- 保持与估算版本对应

### 导出能力

导出格式不作为前期限制项。MVP 可先实现在线报告展示，导出可后续补充。

---

## 9.7 版本与记录模块

### 功能说明

用于支持过程可追溯和多轮估算迭代。

### 核心能力

- 保存历史估算版本
- 保存中间分析结果快照
- 保存用户修改记录
- 保存模型推理过程或摘要
- 支持版本切换与比较（比较可后置）

### 记录类型

- 文档解析记录
- 分析结果记录
- 功能点修改记录
- 成本估算记录
- 重算触发记录

### 设计要求

- 任何影响结果的修改都应可追踪
- 任何重要输出都应可回溯到对应版本

## 10. 交互设计要求

## 10.1 设计风格

整体风格应体现：

- 专业
- 严谨
- 干净
- 简洁
- 科技感但不过度装饰

可参考方向：

- 信息密度适中
- 强调结构清晰
- 视觉优先级明确
- 以表格、卡片、分栏、步骤状态为主

## 10.2 交互原则

- 尽量减少不必要的步骤感
- 以快速进入分析为优先
- 对耗时操作提供明确状态反馈
- 中间结果应可直接查看与编辑
- 避免“只给结果不给过程”的黑盒体验

## 10.3 核心交互特征

- 项目一进入即可看到当前分析进度
- 任何阶段都能回看前置输出
- 用户可在关键中间节点进行修正
- 修正后可重新触发局部或整体重算

---

## 11. 非功能需求

### 11.1 可解释性

系统应尽可能提供中间分析依据、推理说明、计算过程和修改痕迹，以支撑用户理解与复核。

### 11.2 可扩展性

功能点方法、估算模型、文档解析能力应具备后续扩展空间。

### 11.3 可运行性

系统应优先保证可以部署运行，适合个人使用与轻量企业内部使用。

### 11.4 开源友好性

模块边界应清晰，便于后续拆分、贡献和替换。

### 11.5 性能体验

交互应尽快响应。对于文档解析、模型分析、估算等耗时任务，应提供明确的状态提示和阶段反馈。

## 12. MVP 用户流程

### 流程 A：从零开始完成一次估算

1. 用户进入项目列表
2. 点击“新建项目”
3. 填写项目基础信息
4. 上传 PDF 文档
5. 系统完成解析并生成结构化文本
6. 系统自动进行需求分析
7. 系统输出功能识别与 IFPUG 分析结果
8. 系统生成成本估算结果与报告
9. 用户检查中间结果
10. 用户修正若干项
11. 系统重新计算
12. 系统保存新版本

### 流程 B：对已有项目继续迭代

1. 用户打开已有项目
2. 查看历史版本与当前结果
3. 修改中间输出或替换文档
4. 触发重新分析 / 重新估算
5. 系统保存新版本并更新报告

## 13. 成功标准

### 13.1 MVP 成功标准

如果 MVP 达到以下条件，可认为方向成立：

1. 用户能够顺利完成从项目创建到报告生成的全流程
2. 系统能够对 PDF 文档进行基本可用的解析
3. 系统能够生成结构化需求分析结果
4. 系统能够输出可查看、可修改的 IFPUG 分析结果
5. 系统能够根据分析结果生成初步成本估算
6. 用户能够修改中间结果并重新估算
7. 系统能够保存版本、修改记录与关键推理信息

### 13.2 后续评估指标建议

- 一次完整估算流程的完成率
- 中间结果人工修正率
- 用户对解释性的满意度
- 不同版本估算结果的可比较性
- 文档解析可用率

## 15. 一句话总结

这是一个以“项目”为核心对象、以“分析平台”为定位、以“高自动化 + 高可解释性 + 可人工介入”为原则的软件项目规模与成本估算开源系统。其 MVP 重点不在于一次性做全，而在于先跑通“文档驱动的自动分析与可修正估算闭环”，并为后续方法扩展和模型迭代打下基础。
